# Managing LLM Wiki

この Skill は、ユーザーの Obsidian ベースの LLM Wiki を小さく安全な単位で運用する。元資料は `raw/` に不変のまま保管し、長く使う知識は `wiki/` に整理する。ユーザーが明示しない限り、Vault 内の無関係なノートは作業対象にしない。

## 管理範囲

- Vault root: resolve from the `OBSIDIAN_VAULT_PATH` environment variable.
- LLM Wiki root: `$OBSIDIAN_VAULT_PATH/LLM Wiki`.
- 不変の元資料置き場: `LLM Wiki/raw/`.
- 書き込み対象の知識領域: `LLM Wiki/wiki/`, `LLM Wiki/index.md`, `LLM Wiki/log.md`.

この Skill の境界として、次のルールを守る。

- ユーザーが明示しない限り、`Knowledge/`、`Ideas/`、`Inbox/` など既存の別ノート領域を取り込まない。必要な場合も、まず `LLM Wiki/raw/` にコピーしてから扱う。
- `LLM Wiki/raw/` に入った元資料は編集しない。
- wiki 本文は日本語を優先する。
- 内部参照は Obsidian の `[[wikilink]]` を優先する。
- frontmatter は近くのファイルの流儀に合わせる。特に強いローカルルールがなければ、`tags` だけの最小構成を基本にする。
- 変更は小さく戻しやすくする。1 つの焦点化されたノート更新で十分なら、Wiki 全体の再設計をしない。

## 書き込みの許可

- `ingest <資料>` / `/ingest <資料>` の明示的な呼び出し、または資料を LLM Wiki に取り込み・保存・反映する依頼を、指定資料の保存と wiki 更新の許可として扱う。「保存しない」「要約だけ」などの明示的な制限があれば、その制限を優先する。
- `query` と `lint` は既定で読み取り専用とする。保存・反映・修正を明示された場合だけ、許可された範囲で変更する。
- 資料を「読んで・要約して・説明して」という依頼だけなら、回答のみで完了する。URL やパスの提示自体は保存の許可ではなく、`raw/`、`wiki/`、index、log を変更しない。
- 有用な知識や構造的な問題を見つけたこと自体は、書き込みの許可にはならない。未承認の保存候補や修正案は回答内に示し、`index.md` や `log.md` にも書き込まない。

## 最初に向きを合わせる

既存の LLM Wiki に対して作業する前に、必要な範囲だけ現在地を確認する。これにより、重複ページ、既存リンクの見落とし、最近の作業の巻き戻しを避ける。

1. `LLM Wiki/index.md` を読む。
2. `LLM Wiki/log.md` の最近の記録を読む。
3. 作業対象に関係しそうな既存ページを `LLM Wiki/wiki/` から検索する。
4. もし `LLM Wiki/README.md` や `LLM Wiki/SCHEMA.md` のようなローカルルールが存在する場合だけ読む。存在しない schema を新規に仮定しない。

大きな Wiki では、ページ作成や大きめの更新の前に、関連語で `LLM Wiki/wiki/` を検索する。index だけに頼ると、古いページや別名ページを見落としやすい。

## 最初の分岐: 依頼を読む

依頼は原則として次の 3 つに割り当てる。

- `ingest <path>`
- `query <question>`
- `lint <scope>`

ユーザーがこの形式で書いている場合はそのまま扱う。自然文の場合は意図から推定する。

- ファイル、記事、ノート、PDF、Web ページを LLM Wiki に追加・取り込み・保存・反映したい依頼は `ingest`
- 資料を読む・要約する・説明するだけの依頼は、保存を伴わない資料への回答として扱う。既存 Wiki に基づく依頼でなければ、`query` のために Wiki を検索する必要はない
- 既存の LLM Wiki に基づいて答える、説明する、比較する、要約する依頼は `query`
- 健康診断、監査、lint、矛盾、古いページ、孤立ページ、保守不足を探す依頼は `lint`
- 「追加する価値がある情報源を探して」など、まだファイル更新を明示していない依頼は source recommendation として扱い、勝手に `ingest` しない

意図が本当に曖昧なときだけ短く確認する。ユーザーに `ingest` や `query` という語彙を覚えさせる必要はない。

## Workflow: `ingest <path>`

新しい元資料を LLM Wiki に追加するときに使う。

1. パスまたは URL を解決し、「取得品質の確認」に従って依頼された本文を取得できたか確認する。
2. 「再取り込みと処理結果」に従い、既存 raw と処理記録を照合する。
3. 保存が必要な資料だけ、元ファイルを変更せず `LLM Wiki/raw/` にコピーする。図表・添付に依存する場合は「添付資料の扱い」に従う。既存 raw を上書きしない。
4. URL の場合は、URL と取得日が残る形で、できれば cleaned Markdown や exported text としてローカルに不変コピーを保存する。同じ URL の本文が変わっていたら別スナップショットにする。
5. 元資料を読み、今すぐ残す価値がある最小の durable knowledge を見極める。
6. 既存の概念・比較・概説ページを検索し、新資料が既存の主張を支持・修正・反証するか確認する。明確に拡張できるページを優先し、混ぜると濁る場合だけ新規ページを作る。
7. 必要に応じて `LLM Wiki/wiki/` のノートを作成・更新し、影響する既存ページにも反映する。「根拠の追跡」に従って出典と未解決の矛盾を残し、関連ページ間には意味のある参照を設ける。必要な更新を完了できない場合は、対象と理由を報告し、「再取り込みと処理結果」に従って未完了部分を記録する。
8. 「index の管理」に従い、変更したページの掲載内容を `LLM Wiki/index.md` に反映する。
9. 「再取り込みと処理結果」と「log の記録」に従い、`LLM Wiki/log.md` に資料ごとの結果を追記する。
10. コピーまたは再利用した資料、処理結果、変更した wiki ページ、意図的に後回しにしたことを報告する。

### Ingest の注意

- 元資料を保存する。`raw/` は scratchpad ではなく、不変の保管庫である。
- 既存 Vault ノートを資料にする場合も、原本を直接 source として扱わず、まず `raw/` にコピーする。
- 1 つの source から巨大な分類体系を作らない。最初は source summary や焦点化された概念ページで十分なことが多い。
- 新規ノート名は、後から `[[wikilink]]` として使っても意味が通る安定した日本語タイトルにする。
- 10 ファイル以上、または多数の既存ページに触れそうな場合は、作業範囲を確認してから進める。

### 取得品質の確認

- スラッシュコマンド・自然文のどちらから呼ばれた場合も、raw への新規保存と wiki への反映の前に、依頼された本文を取得できたか確認する。本文の短さだけで失敗と判定しない。
- 本文が取得できない、ナビゲーション・認証画面・エラー文しかない、または重要部分の欠落が疑われる場合は、その資料の取り込みを止める。取得できた内容の概要と不確実な点を示し、再試行、別 URL / ファイル、本文貼り付けのどれで進めるか確認する。
- 不完全な取得結果を完全な資料として保存・合成しない。失敗の記録は「再取り込みと処理結果」に従い、確認待ちの間に wiki と index は更新しない。

### 添付資料の扱い

- 主張の理解や検証に必要な図表・添付がある場合だけ、その内容を個別に確認し、必要なファイルを raw 内に保存または再利用する。装飾画像や無関係なリンク先まで収集しない。
- ローカル資料は、本文を変更せず参照を解決できる相対配置で必要な添付をコピーする。Web 資料は、不変コピーを確定する前に、必要な添付を保存してコピー内の参照をローカル保存先に合わせる。
- 既存 raw のリンクを書き換える必要がある場合は、元のスナップショットを残して別スナップショットにする。添付の保存先も「再取り込みと処理結果」に従い、同名ファイルを上書きしない。
- 必要な添付を取得・確認できない場合は「取得品質の確認」に従う。未確認の図表から主張を補わず、欠落を報告する。

### 再取り込みと処理結果

- raw の同一性はファイル名や URL だけでなく内容で確認する。ファイルは内容の比較やハッシュを使い、URL は抽出本文を比較する。知識の根拠として使う添付がある場合は、その内容も照合する。保存時に付けた取得日時などのメタデータの違いだけで別資料にしない。同一内容なら既存 raw を再利用し、元の入力パスまたは URL との対応を log に残す。
- 同名で内容が異なる資料は、拡張子の前に取得日時や内容ハッシュなどを付け、未使用の保存先を選ぶ。同じ URL の更新版もこの方法で保存し、log に旧版の raw パスを併記する。
- raw が既にあることと、wiki への反映が完了していることは別に判定する。処理状況は、同じ raw の内容に対応する最新の log 記録と関連 wiki ページで確認する。最近の log だけに記録がなければ、過去の記録も検索する。
- log は追記式とし、各資料について「入力パスまたは URL」「raw パス（未保存なら未保存）」「結果」「変更した wiki ページまたは理由」を残す。結果は `反映済み`、`確認済み・更新不要`、`失敗` とする。一部だけ反映して中断した場合は `失敗` とし、反映済みの範囲と未完了部分を記す。
- 新たに確認した資料は、wiki の変更が不要でも `確認済み・更新不要` を記録する。取得・反映に失敗した資料は理由を記録する。同一内容について完了記録があり、新しい処理結果も差分もない再取り込みは、raw、wiki、index、log を変更せず再利用・スキップを報告する。明示的に再評価を依頼された場合は再評価する。
- 引数なしの候補探索では、`反映済み` と `確認済み・更新不要` の資料を除外する。`失敗` は再試行候補、完了を確認できない資料は状態不明として区別する。wiki からリンクされていないことだけを未処理の根拠にしない。候補探索と確認待ちの段階では log も変更しない。

### 複数資料の ingest

複数の資料をまとめて取り込むときは、1 件ずつ index と log を更新し続けない。

1. すべての資料を先に確認し、単一資料と同じ取得品質・添付の確認と、「再取り込みと処理結果」による保存・再利用・処理の要否の判定を行う。
2. 資料群に共通する entity、concept、論点を洗い出す。
3. 既存ページ検索と、各資料が既存の主張を支持・修正・反証するかの確認をまとめて行う。
4. 影響する既存ページを含め、wiki ページの作成・更新をまとめて行う。未解決の矛盾と、必要な更新の未完了部分は単一資料と同じ基準で扱う。
5. 「index の管理」に従い、`index.md` の更新を最後に 1 回にまとめる。掲載内容に変更がなければ書き換えない。
6. `log.md` の追記が必要な場合は、資料ごとの結果を含む batch ingest の操作記録を 1 つ残す。全件が差分も新しい処理結果もない再取り込みなら追記しない。

### Ingest の出力形式

ユーザーが別形式を求めていない限り、最後は次の形にする。

1. `Copied to raw`: 元資料のパスまたは URL、保存先または再利用した raw、各資料の処理結果
2. `Updated wiki`: 変更したノートパス
3. `Index/log`: `index.md` と `log.md` の変更有無
4. `Next useful step`: 必要なら次に有用な `ingest` や焦点化された `query`

## Workflow: source recommendation

ユーザーが「LLM Wiki に足すとよさそうな情報源を探して」「このテーマの材料を集めて」のように、更新ではなく候補探しを求めたときに使う。

- 勝手にページ構造を提案したり、`wiki/` を更新したりしない。
- タイトル、URL、残す価値、注意点や不確実性を短く並べる。
- 必要ならニュース、論文、OSS repo、公式ブログ、イベント、動画、展示、ニッチなプロジェクトまで広く見る。
- ユーザーが「取り込んで」「反映して」と明示した時点で `ingest` に切り替える。

## Workflow: `query <question>`

現在の LLM Wiki に基づいて回答するときに使う。

1. `LLM Wiki/index.md` と関連する `LLM Wiki/wiki/` を検索する。
2. 必要な場合だけ関連する `LLM Wiki/raw/` を読む。
3. raw と wiki の両方がある場合は、まず合成済みの wiki ページを優先する。
4. 日本語で簡潔に答え、関連するノートパスを示す。
5. 質問から durable な知識ギャップや有用な新しい関係が見つかったら、保存候補として回答内に示す。保存・反映を明示された場合だけ、根拠を確認して小さく `wiki/` に反映し、index を整えて log に記録する。
6. 新しい資料が必要な場合は、Wiki に既にあるかのように答えず、その不足を明確に伝える。

### Query の注意

- 既定は読み取り専用。保存の依頼がない場合は、回答と保存候補の提示で完了する。
- 保存を依頼された比較、分析、再利用価値の高い synthesis は、将来の検索性を上げる場合に限って wiki に戻す。
- 管理範囲外の Vault 知識を黙って混ぜない。
- 内部知識を引用するときは、クリックしやすいノートパスか `[[wikilink]]` に対応する名前を使う。

### Query の出力形式

ユーザーが別形式を求めていない限り、次の形にする。

1. 短い日本語の回答
2. `Relevant notes`: 参照した主なノートパス
3. `Wiki updates`: `none` または更新したファイル
4. `Gap`: 不足資料や不確実性があれば記載

## Workflow: `lint <scope>`

新しい資料追加や回答ではなく、LLM Wiki の健康診断をするときに使う。

`lint` は、Wiki を長く育つ知識ベースとして保つための保守作業である。スコープは軽く絞る。ユーザーが広い棚卸しを求めていない限り、全体再設計にしない。

- 範囲が指定されていればその範囲、指定がなければ LLM Wiki 全体を診断する。関連ページは根拠確認のために読めるが、修正範囲を勝手に広げない。
- 既定は診断結果と修正案の報告までとし、ファイルを変更しない。修正を明示された場合だけ、指定範囲の問題を修正し、index と log を更新する。

### チェック項目

依頼で観点が限定されていない通常の lint では、対象範囲について次の構造チェックを必ず行う。観点が限定されている場合はその観点を優先し、省略したチェックを報告する。

- 内部リンクと埋め込みの解決先。ページに加え、指定された見出し・ブロックも確認する。
- `index.md` の掲載漏れ、削除・改名後の古い参照。
- 根拠リンクの欠落と、参照する raw 資料・必要な添付の存在。
- 「孤立ページの判定」に基づく、被参照なし・接続なしのページ。
- frontmatter の明らかな欠落や近傍ルールとの不一致。

内容の判断では、対象に関係する既存 wiki と出典を比較し、矛盾・古い主張・重要な根拠不足を優先する。次の観点は対象に応じて選ぶ。

- ページ間の矛盾、新しい source で古くなった主張、根拠と主張の不一致。
- `index.md` の一行説明とページ内容の不一致。
- 複数ページに出てくるのに独立ページがない重要概念、関連ページ間の cross-reference 不足。
- 追加 source や focused web search で埋められそうな情報ギャップ、次に調べる価値がある問い。
- サイズが大きくなりすぎたページ、`log.md` の分割を検討すべき状態。

構造チェックだけで内容も健全と判定せず、実際に確認した観点と未確認の範囲は「Lint の出力形式」に従って報告する。

問題は影響に基づく重要度順に報告する。判断を誤らせる主張・矛盾や重要な根拠の欠落を優先し、broken link、index 不整合、孤立ページなども利用への影響で順位を決める。style issue は原則として後にする。lint によって永続的な変更をした場合は、他の操作と同じく `LLM Wiki/log.md` に記録する。

### 孤立ページの判定

- 知識のつながりは、`LLM Wiki/wiki/` 内の異なるページ間で解決できるリンクで判定する。自己リンク、index・log からの管理リンク、raw への根拠リンク、管理範囲外からの参照は、この判定の inbound/outbound link に含めない。管理リンクや根拠リンクの健全性は別に確認する。
- 他の wiki ページからの inbound link がないページは「被参照なし」、inbound/outbound link の両方がないページは「接続なし」と区別する。outbound link があっても「被参照なし」にはなり得る。リンク数を増やすためだけの修正は提案せず、関連性とページの役割を確認する。
- 範囲を絞った lint でも、対象ページへの参照は `wiki/` 全体から検索する。対象外ページは根拠確認のために読み、修正範囲は広げない。検索範囲やリンク解決が不完全なら、孤立を確定せず疑いとして報告する。

### Lint の出力形式

ユーザーが別形式を求めた場合も、次の情報は残す。

1. `診断範囲`: 依頼された範囲、実際に確認したページ・観点、未確認の範囲と理由。全件確認と部分確認を区別する。
2. `指摘`: 重要度と影響、`確定` / `要確認`、対象ページと該当箇所、根拠となる記述・出典、修正案と影響するページ。矛盾や古い主張では、比較した主張と出典の時点・適用条件を示す。解決できない食い違いは断定しない。
3. `変更`: 診断のみなら `なし`。修正した場合は変更ファイルと index / log の変更有無を示す。Git 同期を行う場合は、その成否・見送り理由も分けて報告する。
4. `未解決・次の確認`: 不足する資料や追加確認が必要な事項。指摘がなくても、全体を健全と断定せず「確認した範囲では検出なし」と報告する。

## ノート作成ルール

wiki ノートを作成または更新するときは、次を守る。

- 日本語と英数字の間は、必要に応じて半角スペースを入れる。
- 句読点は `、。` を使う。
- tag は frontmatter を正とし、内容に合う既存タグを優先する。近傍ルールに必須タグがなく、適切なタグもなければ `tags: []` とする。分野を問わず同じタグを付けない。
- frontmatter はローカルの流儀に合わせる。強いルールがなければ最小にする。
- 見出しで読みやすくする。
- 同じ説明を複数ページに複製するより、隣接概念への `[[wikilink]]` を張る。
- raw extraction より synthesis を優先する。wiki ページは「source に何が書いてあるか」だけでなく「なぜ重要か」を説明する。

## 根拠の追跡

- 作成・更新する知識には、根拠となる `raw/` の資料への `[[wikilink]]` を本文の「根拠」節や脚注に残す。外部 URL だけで済ませず、保存済みの資料へ戻れるようにする。
- 複数資料を合成する場合は、重要な主張ごとに対応する出典を示す。必要に応じて見出し、ページ番号、該当箇所も添える。
- 資料が述べた事実・見解と、エージェントの推論・解釈を区別する。既存 wiki を再利用する場合も根拠の参照を引き継ぎ、確認できない主張は根拠未確認と明記する。出典を推測して補わない。
- 新旧資料が矛盾する場合は、双方の出典、時点、適用条件を残す。新しいという理由だけで旧主張を上書きせず、解消できない食い違いは未解決として示す。

## 改名・統合・削除時の参照整合性

ページの改名・統合・削除、参照される見出し・ブロックの変更では、次を守る。

1. 操作前に、対象への参照を `wiki/` 全体と index から調べる。リンク・埋め込みのページ名だけでなく、見出し・ブロックの指定も確認する。
2. 許可された範囲の参照元を、変更後のページ・該当箇所へ更新する。削除により参照先がなくなる場合は、その参照に依存する説明も修正する。範囲外の編集が必要、または参照調査が不完全なら、構造変更を実施する前に扱いを確認する。
3. `raw/` と log の過去の記録は一括置換や自動リンク更新の対象に含めない。履歴上の旧パスは保持し、変更前後の対応を log の新しい操作記録に残す。自動更新機能を使う場合も、更新対象を許可範囲に限定できる方法を選ぶ。
4. 「index の管理」に従って掲載内容を更新し、今回の変更によって wiki と index の参照が切れていないことを確認する。raw と過去の log に残る履歴参照は、現在の知識ページの broken link と区別する。

## index の管理

- `LLM Wiki/index.md` は、`wiki/` 配下の全 wiki ページを列挙する全件カタログとする。各ページにリンクと一行説明を付け、分類は既存の流儀に合わせる。`raw/` の資料そのものは掲載対象にしない。
- 書き込みが許可された ingest / query / lint でページを新規作成・改名・削除した場合は、対応する項目を追加・修正・除去する。内容の更新で一行説明が古くなった場合も修正する。掲載内容に変更がなければ書き換えない。
- 読み取り専用の query / lint では、不整合を見つけても修正せず報告する。既存の掲載漏れの一括修復は、許可された修正範囲に含まれる場合に行う。

## log の記録

追記する記録は既存の形式を優先する。形式が定まっていなければ、次の最小テンプレートを使う。過去の記録をこの形式へ書き換えない。

```markdown
## [YYYY-MM-DD HH:MM:SS] ingest | 資料名

- 入力: 入力パスまたは URL
- raw: 保存先・再利用先、または未保存
- 結果: 反映済み / 確認済み・更新不要 / 失敗 のいずれか
- wiki: 変更したページ、または更新不要・失敗の理由
```

日時は操作時の絶対時刻に置き換える。batch ingest では 1 つの操作見出しの下に資料ごとの項目を並べ、必要な添付の保存先、旧版 raw、未完了部分も該当資料の項目に添える。書き込みを伴う query / lint は操作名を変え、依頼範囲・変更ファイル・未解決事項を記録する。追記の要否は各 workflow の書き込み許可と再取り込みの判定に従う。

## Git 同期の安全条件

この Skill の利用だけでは commit / push を開始しない。呼び出し元コマンドまたはユーザーが Git 同期を指定した場合に、次を適用する。

1. Wiki の変更前に、Vault 内の `LLM Wiki/` を管理する Git リポジトリ、現在のブランチ、upstream、既存の作業ツリー・staged 変更を確認する。カレントディレクトリのリポジトリを対象だと決めつけない。
2. 今回変更するファイルと既存の変更が重なる場合は、そのファイルを編集する前に扱いを確認する。既存の変更を勝手に stash、reset、破棄しない。
3. コミット対象は、今回追加した `raw/` の資料と、今回変更した `wiki/`、`index.md`、`log.md` の差分だけにする。対象パスを明示して stage し、リポジトリ全体を一括追加しない。既存の staged 変更がある場合は、それを変更せず自動コミットを見送る。
4. 対象差分がなければ commit / push は不要。コミット前に staged 差分が今回の操作だけであることを確認する。
5. push 前に upstream の状態を取得し、送信対象の全コミットと差分が今回の依頼範囲内であることを確認する。既存の未 push コミットが含まれる場合は、自動 push を止めて確認する。履歴の強制書き換えは行わない。
6. リポジトリ・ブランチ・upstream が特定できない、確認が失敗した、または同期に失敗した場合は、勝手に初期化・接続先変更・履歴調整をせず同期を止める。Wiki の更新結果、commit の成否、push の成否や見送り理由を分けて報告する。

## 判断ルール

- Markdown 内容の変更が中心なら、Obsidian で有効な形を保ちながら直接編集する。
- 情報を探すだけなら、ファイル全体を読む前に検索する。
- `ingest` がディレクトリを指す場合は、明確に関連するファイルだけ処理し、スキップしたものを伝える。
- source が noisy または大きすぎる場合は、まず compact summary を作り、深い再編は後続作業に残す。
- ユーザーが広い redesign を求めた場合は、最小の ingest/query 作業とは分けて扱う。

## 完了前チェック

完了前に確認する。

- 書き込みが許可された対象内に収まっている。
- 読み取り専用の query / lint では、index と log を含めてファイルを変更していない。
- `raw/` の元資料を編集していない。
- 新規または更新ノートのタイトルが日本語として自然で、`[[wikilink]]` として使いやすい。
- 変更した知識の根拠を保存済みの資料へたどれ、推論と未解決の矛盾が区別されている。
- ingest では、関連する既存知識への影響を確認し、必要な更新を反映したか、未完了の対象と理由を記録している。
- 構造変更では「改名・統合・削除時の参照整合性」を満たし、今回の変更による参照切れがない。
- 書き込みを伴う場合は、対象ページの追加・改名・削除・説明変更が index に反映されている。
- 永続的な ingest/query/lint 由来の変更が `LLM Wiki/log.md` に記録されている。
- 最終応答で、何を変更したかを具体的に伝えている。
