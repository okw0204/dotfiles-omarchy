# PR 作成まで届ける

元の `implement` を実装手順の正本として使い、その前に作業ブランチを準備し、後に `pr` に沿った PR 作成を行う。ユーザーが明示した例外を優先する。マージやリリースは含めない。

## 1. 作業の前提を確定する

- 依頼された仕様・チケット、対象リポジトリ、作業ツリー、現在のブランチ、リモート、同じ作業の既存 PR を確認する。無関係な変更は保持し、コミットや PR に混ぜない。
- ベースブランチは既存 PR、ユーザーの指定、リポジトリの規約から確定する。指定がなければリモートの既定ブランチを使う。取得できる情報を調べても候補が分かれる場合だけ質問する。
- 新規作業は、確定したベースからリポジトリの命名規約に沿う作業ブランチを作り、編集前に切り替える。同じ作業のブランチや PR がある場合は継続する。無関係なブランチのコミットを新しい PR に持ち込まない。
- 切り替えに既存変更の破棄・退避などの判断が必要なら、ユーザーに確認する。既存変更を勝手にリセット、退避、コミットしない。
- レビューに渡す比較基準のコミット SHA と仕様の参照先を記録する。既存 PR の継続では、今回の開始時点ではなく PR 全体の差分を対象にできる基準を選ぶ。

## 2. 元の implement を実行する

実行環境が示すスキル一覧・保存先から、インストール済みの `implement/SKILL.md` を特定して読み、その指示を現在のセッションで実行する。スキル呼び出し機能で読み込めない場合もファイルを直接読む。見つからない場合は依存スキル不足として報告し、記憶から手順を代用しない。

- 元のスキルは変更も複製もしない。参照先の相対パスは、そのスキルのディレクトリを基準に解決する。
- `tdd` や `code-review` など、元のスキルが要求するスキルも必要なタイミングで読み込む。テスト対象の境界について既存の合意があれば引き継ぎ、なければテストを書く前に合意する。
- `code-review` がコミット済みの `HEAD` を対象にする場合は、未コミットの変更を見落とさないよう、検証済みの作業分を先にコミットしてからレビューする。これが元の手順に対する順序の補正となる。
- レビューには手順 1 の比較基準と仕様を渡す。指摘を評価し、必要な修正・再検証・コミット・再レビューを行い、提出を妨げる未解決事項がない状態にする。採用しない指摘は理由を示す。

元の `implement` のコミット完了は途中段階であり、ここで終了せず PR 作成へ進む。

## 3. PR を作成・更新する

インストール済みの `pr/SKILL.md` を読み、その構成に沿って本文を書く。依存スキルが見つからなければ報告する。リポジトリの PR テンプレートや言語・表記ルールも守り、観測済みの証拠と未検証事項を区別する。

- リポジトリの公開先に対応した利用可能な CLI または連携機能で作業ブランチを push し、確定したベースに対して PR を作成する。同じ head/base・同じ作業の既存 PR があれば、新規作成せず更新する。
- レビュー後の修正も含む最終コミットがリモートに反映され、PR の head/base が意図どおりであることを確認する。履歴の強制更新や自動マージは行わない。

## 4. 結果を報告する

完了報告には PR の URL、変更の要点、実際に行った検証と結果、残る注意点を含める。PR 作成・更新と最終コミットの反映まで確認できた場合に完了とする。公開が妨げられている場合は、ローカルの完了範囲と未完了の公開操作を分けて伝える。
